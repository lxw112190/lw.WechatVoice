# preview16：只读副本加速与进度

2026-11-10。

## 对原程序的影响范围

- 源数据库和 WAL 用 `FileAccess.Read` 打开，并允许微信继续读写或替换文件。不会在源目录运行 SQLite 查询、写 journal/SHM、执行 checkpoint 或解密源文件。
- 选定 PID 的密钥扫描申请查询和读取内存权限，没有写进程内存、注入、修补程序或结束微信的操作。
- 文件复制、认证、解密、WAL 重放、SQLite 完整性检查和索引都在工作目录内的私有文件上完成。输出不能位于源账号目录。
- 读取仍消耗 CPU、磁盘带宽及系统缓存，可能短时影响原程序响应；不承诺“完全零影响”。本次没有新增并行读取多个库，以免同盘争用。

## 加速方法

1. 每个数据库复用独立 HMAC/AES 上下文。页 MAC 子密钥只按该库的 key/salt 派生一次；每页仍认证页号、密文、IV，每页重设 CBC IV，库之间不共享状态。WAL 的 checksum、页认证、已提交前缀和旧代际结尾判断不变。
2. 顺序复制及解密输入/输出使用 1 MiB 文件缓冲，循环复用页/帧数组，减少小块 I/O 和内存分配。只检查首页密钥时仍用 4 KiB 缓冲。
3. 已经是明文的 SQLite，在主库/WAL 对复制并确认源签名稳定后，直接对**本工具创建的冻结副本**重放 WAL、执行 quick_check，再发布为只读副本，省掉第二遍完整读写。不会对原库使用此路径。
4. 界面显示当前库编号、复制/解密/WAL 校验/WAL 合并/完整性检查阶段、MiB 进度及处理速度。诊断日志只保留阶段、字节数、耗时、速度，不增加路径、密钥或聊天内容。

## 本机性能对比

相同的 33,644,544 字节（约 32.1 MiB）合成数据库，preview15 与本版交替运行三轮，取中位数；耗时包括在线冻结复制、解密/WAL 和 SQLite 完整性检查。每次输出均校对 SHA256；加密副本与 Python 参考结果比较，保留区也保持一致。

| 数据类型 | 优化前 | 优化后 | 比值 |
| --- | ---: | ---: | ---: |
| 加密 SQLite | 1.528 秒 | 0.233 秒 | 约 6.6 倍 |
| 明文 SQLite | 0.309 秒 | 0.241 秒 | 约 1.3 倍 |

这不是所有机器的速度保证。机械硬盘、大型活跃 WAL、数据库大小及微信写入频率都会影响结果；源数据持续变化时仍最多重试三次，不绕过一致性校验。

## 验证

- 加密/WAL 对照扩大至 15 个用例，增加多页复用及末页篡改拒绝。
- `SnapshotCheck`：对源库和 WAL 持有禁止写入共享的只读句柄，验证全部成功/拒绝结果、输出字节及源内容/修改时间/文件列表不变；未产生源 journal/SHM。
- 覆盖复制、解密、完整性检查阶段边界的取消与临时文件清理，以及复制期间源文件发生变化后的重试。
- 实际消息循环检查详细进度文案与进度条；诊断 ZIP 检查新增性能字段可用且私密字段仍被过滤。

测试使用合成库和合成进程，本轮未读取真实聊天或真实微信进程内存；C# 引擎的真实账号兼容性仍需授权复测。
