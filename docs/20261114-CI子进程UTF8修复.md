# CI 独立解码的 UTF-8 BOM 修复

失败运行：[43594644990 / Windows job](https://github.com/lxw112190/lw.WechatVoice/actions/runs/43594644990/job/132446446672)。单条、多条、结束标记及截断等直接解码用例全部通过，后续独立解码子进程失败。

## 复现与根因

在本机将 CodecCheck 的 Console.InputEncoding 显式设为 Encoding.UTF8，同一套音频用例复现 CI 相同的失败。Windows .NET Framework 的 Process.StandardInput 使用宿主输入编码；UTF-8 模式下，其 StreamWriter 初始化可能先写出 BOM，之后的 BaseStream UTF-8 JSON 前就带有该前导。

子进程原先使用 Console.In，它没有识别这个 BOM，JavaScriptSerializer 因此无法把首行解析成请求。父进程只显示“语音解码失败”，容易误认为原生解码器本身出错。

## 修改

VoiceEngine 和 AsrWorker 的标准输入改为显式 StreamReader，启用 BOM 检测，再交给原有 NDJSON 解析。只在输入流开头处理前导，不在每个 JSON 内随意删除字符；保留原有校验和解码限制。

CodecCheck 固定覆盖代码页 437 与 65001，继续比较完整 WAV 字节、包数、时长、拒绝情况与取消后无延迟写入。IpcCheck 强制使用 UTF-8 控制台；识别假进程与真实识别进程使用一致的输入流边界处理。
